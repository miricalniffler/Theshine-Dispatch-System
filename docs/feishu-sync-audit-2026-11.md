# 飞书同步助手审计（2026-11-05）

## 已确认的实现问题

- 初始实现 `4e4126679ec69e9f43184f9464b1f65f2cbb95d6` 已包含本地订单邮件读取与导入。随后同步脚本陆续增加了超时、stale-run 清理、最近邮件缓存、城市/时区判断、多个邮件格式解析和并发保护。仅凭提交先后不能断言每项补丁造成了故障，但它们让执行状态、重试和进度判断分散在脚本、网页路由及数据库记录中。
- 当前页面的“同步飞书”请求在本机模式下只等待最近一次定时运行；它没有建立可被本机助手领取的请求。这使周期运行和用户点击无法关联。现已改为创建一个 `REQUESTED` 同步记录，由现有本机轮询任务领取；页面按请求 ID 读取结果，且超过 10 分钟未领取的请求会在助手恢复后标记失败。
- 旧脚本每个发件人只请求最新 200 封摘要。缓存去重不能弥补列表窗口之外尚未处理的邮件。现已使用 `+triage` 返回的分页令牌逐页读取全部匹配摘要；进程中断后从第一页重读，已写入的邮件由消息 ID 去重。
- 本机脚本同时使用 `spawnSync` 75 秒超时、120 秒总 watchdog、数据库连接超时和 5 分钟 stale-run 清理。特别是 watchdog 直接退出时，当前记录可能暂时保持 `RUNNING`，然后被后续任务判为 stale。它们是需要继续精简和验证的执行保护，不应被视为同步成功证明。
- LaunchAgent 工作目录和 `lark-cli` 默认路径写死在脚本中；仓库没有 Mac 上的 plist、实际脚本校验值或本地运行日志。因此 GitHub 版本无法证明 Mac 已运行该版本，也无法证明授权、数据库连接或定时任务正常。

## 事务和恢复检查

- 新订单唯一订单号与来源邮件唯一键分别提供幂等保护。
- 本机脚本先写订单、后写邮件来源记录。如果在两步之间中断，后续扫描会识别已存在订单并补写来源记录；不会把读取完成当成数据库提交成功。
- 同步记录最终状态由订单处理循环完成后写入；数据库不可用时，不能显示成功。仍需在真实 Mac 环境演练进程终止和数据库超时恢复。
- Gmail 与飞书分别保留 connector/message ID；现有订单号唯一索引可阻止同一平台订单被两边重复创建。

## 本次更改及未验证边界

- 网页点击会创建明确的 `REQUESTED` 记录；LaunchAgent 下一轮（目前配置未知）领取相同记录并写最终状态。网页按请求 ID 匹配结果，避免把无关的周期同步误报为点击触发的完成。
- 飞书摘要读取改为全量分页，数据库中已处理的 source message 仍用于避免重复下载正文。
- 自动化回归用模拟分页覆盖 450 封邮件、令牌延续、令牌重复和不完整响应；这不能替代真实 `lark-cli`、Mac 重启、网络故障或生产数据库验证。
- 真实邮箱的 API 授权依赖本机已登录的 `--as user` 身份。云端迁移前必须实际确认服务账号/用户授权、邮箱权限和令牌续期方式；目前没有证据支持安全迁移到 Vercel。

## 第二轮代码复核：以恢复最初简单可靠为目标

以下是静态代码确认的问题，不是 Mac 现场故障结论：

1. **全量扫描与总超时互相冲突**：`fetchAllTriagePages` 每轮从第一页扫描两个发件人的所有历史摘要；主脚本默认 `IWAY_LOCAL_SYNC_MAX_RUN_MS=120000`，单次 `spawnSync` 超时 75 秒。邮箱增长会提高每轮成本，不能仅凭 450 封模拟测试宣称长期可靠。
2. **外层 watchdog 不能打断阻塞的 CLI**：`spawnSync` 阻塞 Node 事件循环，120 秒 JavaScript timer 无法在 CLI 阻塞期间准时触发。应优先用可取消的异步子进程执行器，并为每次运行设明确预算。
3. **网页请求只是队列，不是 Mac 唤醒机制**：请求写入 `ImportSyncRun.REQUESTED`，需要 LaunchAgent 实际启动并读取同一个 Production 数据库才能领取。页面必须清楚区分「已排队」「执行中」「已完成」「超时」。
4. **旧注释与行为矛盾**：当前本机助手只导入新订单、排除修改和取消，但其缓存注释声称「修改邮件会自动读取并覆盖订单」。这会误导运维与后续维护，应删除。
5. **没有可验证的持久增量游标**：当前每轮全量扫描历史摘要，仅以 `ImportedSourceMessage` 去重正文。正确方向是使用已确认的服务端分页与安全重叠窗口/水位线，并设计崩溃恢复，不能重新引入只看最新 200 封的漏单问题。
6. **真实运行证据缺失**：Mac 的 LaunchAgent plist、脚本路径、实际 commit、`lark-cli` 授权、日志和生产 DB 实例均未验证。合并前应完成至少一次真实端到端验证。

### 继续开发的最小化原则

- 保留一个本机进程、一个 CLI 读取入口、一个数据库提交路径和一个清晰的同步状态机；不要叠加第二套调度器。
- 新订单导入仍保持只新增，不意外覆盖已派单订单；修改/取消由另一个已审计的安全事件处理器承担。
- 将「安全不漏单」和「每轮扫描成本有上界」同时纳入验收；在未证实 CLI 提供可靠的增量语义前，不要凭猜测截断历史。
- 优先清理过期注释、修复错误状态和可复现超时，再考虑架构扩张。
